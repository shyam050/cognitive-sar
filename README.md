# Cognitive Multi-Robot Search and Rescue

Collaborative perception + reasoning for multi-robot SAR (DA project, team
23BRS1268 / 23BRS1209 / 23BRS1192 / 23BRS1227).

Three simulated robots explore a collapsed-structure world, fuse their maps
into one global grid (O1), detect victims and share them through a common
semantic memory (O2, O3), and a MAPPO policy trained with
centralized-training/decentralized-execution allocates search regions (O4) —
benchmarked against a rule-based allocator (O5).

```
ROBOT i (x3)                    SHARED STATE                REASONING
 slam_toolbox ─┐                 map_merge ─► /map_merged    MAPPO actor (O4)
 YOLO/HSV det ─┼► /detections ─► sar_memory ─► /semantic_map   or rule baseline (O5)
 Nav2 ◄── /robot_i/goal ────────  frontier ──► /regions      sar_eval metrics
```

## Quick start (WSL2, Ubuntu 24.04)

```bash
# 1. one-time environment setup (ROS2 Jazzy + Gazebo Harmonic + deps)
bash scripts/install_wsl.sh

# 2. build
cd ~/cognitive-sar/ros2_ws
colcon build --symlink-install
source install/setup.bash

# 3. rule-based mission (baseline, no checkpoint needed)
ros2 launch sar_bringup multi_sar.launch.py robots:=3 allocator:=rule

# 4. RL mission (after training, section below)
ros2 launch sar_bringup multi_sar.launch.py robots:=3 allocator:=rl \
    checkpoint:=~/cognitive-sar/training/runs/mappo_v1/checkpoint_best.pt
```

Watch RViz: merged map grows, cyan cubes are frontier regions, orange spheres
are located victims. `sar_eval` writes `~/sar_results/metrics_*.csv`.

## Training the allocation policy (O4)

The policy trains on a lightweight grid abstraction of the world (region-level
actions, A\* executor) — minutes on CPU, faster on GPU.

```bash
cd training
pip install -r requirements.txt

python train.py --steps 150000 --seed 0          # full run (~1.5 h CPU, ~15 min GPU)
python train.py --steps 30000                    # quick sanity run
python evaluate.py --checkpoint runs/mappo_v1/checkpoint_best.pt --maps 6
```

`evaluate.py` benchmarks **mappo vs rule_based vs random** on unseen maps
(coverage, victims, mean detection time, overlap) and writes
`runs/<run>/eval_results.json` — the same comparison is then repeated inside
Gazebo via allocator:=rule vs allocator:=rl for the final report.

No GPU on your laptop? The run is CPU-friendly, or use Colab (Runtime →
change runtime type → GPU; upload `training/`, `pip install -r
requirements.txt`, run the same command, download `runs/mappo_v1/`).

> **Contract:** `sar_alloc_rl/obs_contract.py` mirrors the training observation
> spec exactly and is verified by unit tests (`test_obs_contract.py`) — if you
> change network or observation code, rerun those tests before deploying.

## Regenerating the world

The Gazebo world, victim placement and ground truth come from the same maze
code the RL env trains on:

```bash
python scripts/gen_world.py --seed 0     # writes sar_worlds/worlds/… + sar_eval/config/ground_truth.yaml
```

## Benchmarks & metrics (O5)

Run each configuration ≥10 times (different seeds change nothing here — the
world is fixed; vary `--seed` in gen_world or run times), then compare
`allocator:=rule` vs `allocator:=rl` CSVs with the plotting script:

```bash
python ros2_ws/src/sar_eval/scripts/plot_results.py ~/sar_results/metrics_*.csv -o ~/sar_results/figs
```

Metrics: coverage %, victim detection accuracy, time-to-detection, task
allocation efficiency (overlap ratio), plus RL-side episodic reward and
episodes-to-convergence from `training/runs/<run>/metrics.csv`.

### Expected first-run tuning (normal!)

- **Nav2**: costmap sizes/inflation may need adjustment; if a robot refuses to
  plan, check `/robot_i/scan` is alive and TF `map → robot_i_odom → robot_i_base_link` is connected in RViz.
- **slam_toolbox**: adjust `max_laser_range` to match the lidar (5.0 m).
- **detector**: HSV range is tuned for the orange victim models; switch
  `model_type:=yolo` once you've fine-tuned weights on sim frames.
- **Gazebo in WSLg**: if the GUI is slow, run headless (`gz_args: -s -r <world>`)
  and keep only RViz.
